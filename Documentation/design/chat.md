# Text chat and voice chat: channels, effects and data flow

Status: current alpha tree. This document covers the chat layer as a whole: the
text-chat service contract a game composes on top of the session transport, the
voice runtime, and the fixed-state voice effect system that adds mumbling,
underwater filtering, oxygen-condition readout, voice modulation, positioning
and radio interference. The low-level transport is described in
[networking.md](networking.md) and [security.md](security.md); the voice capture
and codec path is described in [voice.md](voice.md).

Text chat is documented here as a service contract: the engine supplies the
transport, session, text and accessibility primitives, while the channel
policy, message store and moderation commands live in the game or a chat
plugin. Voice chat and its effect chains are implemented by the engine modules
described below.

The two chat kinds share three rules:

1. The network carries messages, not presentation objects. Channels, effects and
   captions are local state.
2. Every buffer has a fixed capacity. Chat and voice must keep running when a
   player floods, a packet is malformed or a device disappears.
3. The authority validates what it forwards. A client can request a mute, a
   voice effect or a message, but the receiving side decides what it renders.

## 1. Layer map

| Layer | Responsibility | Typical owner |
|---|---|---|
| Transport | Datagrams, reliability, fragmentation, encryption | `Net::Transport`, `Net::SecureChannel` |
| Session | Player slots, ticks, reliable events, roster | `Net::NetSession` |
| Chat protocol | Message framing, channel ids, validation, rate limits | game or chat plugin |
| Chat store | History, subscriptions, mute list, unread state | game or chat plugin |
| Voice runtime | Capture, AEC, denoise, Opus, jitter, decoded rings | `VoiceSystem`, `VoiceChannel` |
| Voice effects | Per-stream DSP, conditions, state readout, spatial routing | `VoiceEffectRack`, `VoiceEffectChain` |
| Presentation | Text layout, captions, indicators, particles | UI, accessibility and particle systems |

Text chat is not coupled to voice chat. A game can ship text only,
voice only, or both. When both exist, the same player id and the same mute list
should drive the two paths so a mute is one user action.

## 2. Text chat organization

### 2.1 Channel model

A channel is a small value type with a stable numeric id, not a pointer to UI
state. Recommended channels:

| Kind | Visibility | Authority policy | Example |
|---|---|---|---|
| System | Local only | Generated by the game | "Server restarting in 60 s" |
| Global | Everyone | Server broadcast | Trade or help |
| Team | Team members | Server filters by team | Team tactics |
| Party | Party members | Server filters by party | Group coordination |
| Proximity | Nearby players | Server or client distance check | Local roleplay |
| Whisper | One recipient | Server routes privately | Direct message |
| Command reply | Requester only | Local command parser | "/who", "/mute" |

Recommended limits:

| Constant | Suggested value | Reason |
|---|---|---|
| Maximum channels | 8 | Fits a tab strip and a fixed subscription array |
| Maximum message bytes | 256 | One reliable frame after the header |
| Maximum history per channel | 128 | Bounded scrollback and memory |
| Maximum muted players | 64 | Bounded moderation list |
| Maximum rate-limit entries | 8 per player | One bucket per player |
| Maximum pending unread | 32 per channel | Bounded badge state |

The channel id is serialized as a 16-bit value. `0` is reserved for system
messages so a malformed remote frame can never claim it. Names are localization
keys, not free text, so the UI can switch language without rewriting history.

### 2.2 Message record

A chat message is plain UTF-8 plus metadata. It is not rich text. Markup is
parsed only by the presentation layer and only from a safe subset.

| Field | Type | Rule |
|---|---|---|
| Protocol version | `uint8` | Reject unknown versions |
| Channel id | `uint16` | Must be subscribed and non-zero for remote text |
| Flags | `uint8` | System, emote, whisper, censored, offline |
| Sender player | `uint8` | Taken from the authenticated session, never from the payload |
| Sender sequence | `uint16` | Per sender, wrap-safe, used for deduplication |
| Server tick or time | `uint64` | Sort key for history and captions |
| Text length | `uint16` | 0..256 bytes, not code points |
| Text | UTF-8 bytes | No NUL, no control characters, no bidi overrides |
| Local timestamp | `uint64` | Presentation only, not trusted for ordering |

The sender id in a received frame is always replaced with the session slot that
authenticated the packet. A payload field with a sender id is either absent or
ignored. This is the same rule the voice packet uses for `FVOX`.

### 2.3 Delivery and ordering

`NetSession::SendEvent` payloads are limited to 64 bytes and are already
reliable and ordered. A chat message of up to 256 bytes therefore needs one of
two explicit policies:

1. A dedicated reliable chat message type with a larger payload and its own
   sequence space.
2. A fragment envelope: a chat message id, a fragment index, a fragment count
   and up to 48 text bytes per event.

The second policy is easier to add to an existing session and is recommended for
a first implementation. The receiver reassembles only up to the maximum message
size and drops the whole message on a gap, a duplicate or a timeout.

Ordering rules:

- The authority assigns a monotonically increasing `ServerTick` or room
  sequence to each accepted message.
- Clients display messages sorted by that value, with a stable tie-breaker on
  the sender id and sender sequence.
- A client never trusts a remote wall-clock timestamp for ordering.
- Reconnect history is a bounded snapshot of the last 128 messages per channel,
  not a replay of every event.
- A late joiner receives history after the join snapshot; messages sent before
  the join are not replayed unless the game explicitly requests a transcript.

### 2.4 Rate limiting and flood control

A token bucket per player is enough:

| Setting | Suggested value | Meaning |
|---|---|---|
| `Burst` | 5 | Messages available after an idle period |
| `PerSecond` | 2 | Refill rate |
| `SlowModeSeconds` | 1 | Minimum interval in a public channel |
| `DuplicateWindowSeconds` | 3 | Identical text in the window is dropped |
| `MaxQueuedMessages` | 32 | Per-connection outbound queue |
| `FloodMuteSeconds` | 10 | Temporary silence after repeated violations |

The server applies the limit before validation and forwarding. The client applies
a softer local limit so the input box never promises a send that the server will
drop. The authority should treat every rejected message as a counter, not as a
reason to disconnect; repeated violations can escalate to a kick through the
normal moderation path.

### 2.5 Sanitization

Text sanitization runs before storage and again before rendering:

1. Validate UTF-8 and reject invalid sequences.
2. Remove C0/C1 control characters except a normalized newline.
3. Remove bidirectional overrides, zero-width characters and other invisible
   ordering characters unless the game explicitly supports RTL composition.
4. Collapse repeated whitespace and trim leading/trailing whitespace.
5. Truncate at a UTF-8 code-point boundary, never in the middle of a sequence.
6. Escape or strip markup. The renderer owns the safe markup subset.
7. Apply the profanity or link policy after escaping, so filtering cannot be
   bypassed by inserting markup characters.
8. Store the sanitized string, not the original, unless the game has a lawful
   moderation-retention policy for the original.

The same sanitizer feeds captions, logs and the text-to-speech path. A caption
must not render markup that the chat window stripped.

### 2.6 Mute, ignore and moderation

A local mute is a client-side filter: the message is still received and stored
if the channel history needs it, but it is not rendered. A server mute is a
permission change: the authority rejects the send. Keep the two states separate
so a player can ignore someone without asking the server to police them.

Recommended moderation commands:

| Command | Effect | Authority |
|---|---|---|
| `/mute Player` | Local ignore list | Client |
| `/unmute Player` | Remove local ignore | Client |
| `/voice-mute Player` | Local voice mute or mumble | Client |
| `/ban Player` | Remove from the session | Server |
| `/slowmode Seconds` | Channel rate limit | Server |
| `/announce Text` | System message | Server |

The voice path reads the same local ignore list. A text ignore does not have to
imply a voice mute, but the UI should offer both in one place.

### 2.7 UI and accessibility

The chat view is a virtualized list over a fixed history ring. The input box
supports IME composition, paste normalization and a bounded command history.
Unread counts are per channel; the tab strip shows at most eight channels.

Accessibility requirements:

- Every message has a speaker label and a channel label, not only a color.
- New messages can be mirrored into the narrative log through the accessibility
  kernel.
- Deaf mode can caption voice chat through `VoiceCaptionProvider`; text chat
  should not duplicate the same line as both a chat message and a caption unless
  the player enables both.
- Text scale, contrast and safe-area layout come from the UI theme; the chat
  layer never hard-codes pixel sizes.
- A "new message" cue uses the sound-cue registry with its own category so it
  can be muted independently from voice.

### 2.8 Text chat configuration example

A game-side configuration can be a small value object. The exact storage format
is up to the project; the following fields are the complete policy surface used
by the flow above.

```cpp
struct TextChatConfig
{
    std::uint32_t MaxMessageBytes = 256;
    std::uint32_t MaxHistoryPerChannel = 128;
    std::uint32_t MaxChannels = 8;
    std::uint32_t MaxMutedPlayers = 64;
    std::uint32_t Burst = 5;
    std::uint32_t PerSecond = 2;
    float SlowModeSeconds = 1.0f;
    float DuplicateWindowSeconds = 3.0f;
    float FloodMuteSeconds = 10.0f;
    bool AllowLinks = false;
    bool AllowMarkup = false;
    bool EchoOwnMessages = true;
    bool PersistLocalLog = false;
};
```

A matching project fragment, if the game stores the policy in TOML:

```toml
[chat]
max_message_bytes = 256
max_history_per_channel = 128
max_channels = 8
burst = 5
per_second = 2
slow_mode_seconds = 1.0
duplicate_window_seconds = 3.0
allow_links = false
allow_markup = false
echo_own_messages = true
persist_local_log = false
```

### 2.9 Send and receive flow

Send:

1. The UI asks the chat service to submit text for the active channel.
2. The service trims, validates, measures the UTF-8 byte length and applies the
   local token bucket.
3. The service emits a local echo with a pending state if `EchoOwnMessages` is
   enabled.
4. The service encodes one message or a fragment envelope and sends it to the
   authority.
5. The authority authenticates the sender, checks the channel permission, rate
   limit and mute state, sanitizes again and assigns the room sequence.
6. The authority broadcasts the accepted message to every subscriber, including
   the sender so the client can replace the pending echo.

Receive:

1. The session hands an authenticated payload to the chat service.
2. The service validates the version, channel, sender and length.
3. The service reassembles fragments, rejects gaps and duplicates, then
   sanitizes.
4. The service appends the message to the bounded history ring and increments
   the unread count.
5. The UI drains new messages once per frame; the accessibility layer receives
   the same event without re-parsing the text.

## 3. Voice chat organization

### 3.1 Runtime path

The implemented voice path is:

```text
microphone -> raw ring -> AEC -> denoise/gate/AGC/limiter
           -> uplink effect chain -> Opus -> FVOX packet -> transport
transport -> FVOX packet -> jitter buffer -> Opus decode/PLC/FEC
          -> downlink effect chain -> participant ring -> Voice bus -> mixer
```

`VoiceSystem` owns the capture path and the channel. `VoiceChannel` owns the
jitter buffers, Opus decoders and per-participant rings. `VoiceSession` owns
participant state, mute/deafen/push-to-talk policy, talking indicators and
listener-side spatial placement.

### 3.2 Where an effect belongs

| Effect | Uplink | Downlink | Why |
|---|---|---|---|
| Radio on the speaker's own microphone | Yes | No | Every listener hears the same radio voice |
| Listener-side mumble or mute | No | Yes | Each listener can mute or mumble independently |
| Underwater because the listener is submerged | No | Yes | It is a property of the listener's environment |
| Underwater because the speaker is submerged | Optional | Yes | Either side can own the replicated state |
| Held-head voice at another position | No | Yes | Position is listener-relative |
| Pitch/formant change for everyone | Yes | No | The speaker's identity is modified at the source |
| Pitch/formant change for one listener | No | Yes | The listener chooses the presentation |
| Oxygen readout for game-owned bubbles | Local | Per participant | Oxygen is game data; the engine only passes it through |

The rule is simple: apply an effect on the side that owns the state that drives
it. If every listener must hear the same transformation, put it in the uplink
chain. If the transformation is a local preference, a local environment or a
local position, put it in the downlink chain.

An underwater scene usually needs both audio paths: `AudioZoneSystem` applies the
world and music low-pass for the listener's zone, while `VoiceEffectRack` applies
the per-participant voice filter and warp. They are separate because voice also
carries spatial placement and a read-only condition snapshot for the game.

Ready-made effects are data, not code. `VoicePresetRegistry` holds named
`VoiceEffectProfile` values loaded from `.fbyvoice` packs or registered by a
plugin; `VoiceEffectPolicy` decides what a moderated participant sounds like, and
`VoicePresetApplier` copies the resolved value into the rack only when it
changes. A listener-side `Mumble` policy therefore cannot be bypassed by the
sender: the speaker's packet carries speech, not the presentation.

Reactive cues such as bubbles, splashes and a muffled thump are a separate local
layer (`VoiceReactiveSfx`). They are triggered by participant state, never by a
remote packet, and they play on the Sfx bus at the speaker's position. They are
deliberately not mixed into `FVOX`; see
[voice presets](voice-presets.md) for the limit and asset rules.

### 3.3 Chain architecture

A `VoiceEffectRack` is the per-stream unit. It combines:

- an authored `VoiceEffectProfile`;
- a fixed `VoiceEffectChain` with up to eight serial slots;
- two reserved condition slots (underwater and radio) when conditions are
  enabled;
- a condition smoother and a read-only condition snapshot.

A `VoiceEffectChain` is a serial list of `VoiceEffectSlot` values. Each slot has
a kind, a wet/dry `Mix` and one parameter group per kind. The chain is
fixed-state: configure once, then process any block size. Slot parameters can be
updated between blocks without dropping filter or delay history, and the mix is
ramped over about 6 ms to avoid clicks.

Key properties:

- one delay line per slot, 2048 samples at 48 kHz;
- one-pole or biquad filters per slot, no per-sample allocation;
- all DSP state is plain data in fixed-size arrays, so a rack has a stable
  footprint and no hidden allocation; the rack is non-copyable by design;
- the DSP runs on the game thread in `VoiceSystem::Tick` and
  `VoiceChannel::Tick`, not on the audio callback;
- the audio callback only consumes the resulting `FloatRing`.

Update cadence matters:

| Call | When |
|---|---|
| `SetUplinkEffects` | Start-up or when the local profile changes |
| `SetParticipantEffects` | When that participant's profile changes |
| `SetLocalCondition` | Every frame that advances oxygen or interference |
| `SetParticipantCondition` | Every frame for each remote source |
| `SetParticipantPosition` | Every frame or when the entity moves |
| `SetParticipantPositionOverride` | While the override is active |
| `VoiceSystem::Tick` | Once per frame |
| `VoiceSession::Update` | Once per frame |

`SetUplinkEffects` and `SetParticipantEffects` rebuild the chain and reset its
filter history. Do not call them every frame; use the condition and position
setters for per-frame changes.

`VoiceSystemConfig::UplinkEffects` supplies the initial local profile at
`VoiceSystem::Start`; participant racks start with a condition-capable empty
profile and are replaced through `SetParticipantEffects`.

### 3.4 Presets

`VoiceEffectPresetChain` returns a ready chain for the common cases.

| Preset | Slots | Intended use |
|---|---|---|
| `None` | Empty | No processing |
| `Muted` | Mute | Direct silence with a short fade |
| `Mumbling` | Muffle | Low, saturated, wobbling speech that stays audible |
| `Underwater` | Underwater | Resonant low band and wow |
| `Radio` | Radio | Narrow band, static, crackle and squelch |
| `RadioMuted` | Radio, Mute | Radio texture followed by direct silence |
| `Chipmunk` | Pitch +12, Formant +6 | Held-head or cartoon voice |
| `Deep` | Pitch -7, Formant -4 | Large or masked speaker |
| `Robot` | Ring modulation, Distortion | Synthetic voice |
| `Whisper` | Whisper | Breathy, quiet speech |

A preset is a starting point. Every field can be changed after the chain is
built, and `VoiceEffectChainSettings::Issue()` reports when a value was outside
its supported range.

## 4. Voice effect settings reference

A `VoiceEffectProfile` contains three fields:

| Field | Meaning |
|---|---|
| `BaseChain` | Authored `VoiceEffectChainSettings`, up to eight slots |
| `Conditions` | `VoiceConditionSettings` for the reserved underwater/radio path |
| `EnableConditions` | When false, the condition path is bypassed entirely |

The effect kinds are:

| Kind | Processing | Approximate latency | Notes |
|---|---|---|---|
| `Mute` | Gain fade to zero | Fade time | Direct silence |
| `Muffle` | High-pass, two low-passes, saturation, tremolo, breath | None | Unintelligible but audible |
| `Underwater` | High-pass, two low-passes, resonant peak, wow | Up to 20 ms delay tap | Listener or speaker environment |
| `Radio` | Band-pass, drive, static, crackle, squelch | None | Narrow-band radio |
| `Pitch` | Two-tap granular delay | Up to one window | Pitch only |
| `Formant` | Three peaking resonators | None | Timbre colour |
| `Distortion` | Drive, quantizer, band limit | None | Harsh or robotic |
| `RingModulation` | Sine multiplication | None | Metallic or robot |
| `Whisper` | High-pass, low-pass, shaped noise | None | Breathy speech |

All frequencies are hertz, all gains are decibels unless the field says
otherwise, and all times are seconds unless the field ends in `Ms`.

### 4.1 `VoiceMuteSettings`

| Field | Range | Default | Meaning |
|---|---|---|---|
| `FadeSeconds` | 0..2 | 0.08 | Time for the gain to reach silence; 0 is immediate |

### 4.2 `VoiceMuffleSettings`

| Field | Range | Default | Meaning |
|---|---|---|---|
| `LowCutHz` | 20..1000 | 120 | High-pass corner; removes rumble below the mumble band |
| `HighCutHz` | 100..12000 | 620 | Low-pass corner; the main intelligibility control |
| `Resonance` | 0.1..8 | 1.0 | Q of the first low-pass stage |
| `DriveDb` | 0..36 | 9 | Saturation drive |
| `WobbleHz` | 0.1..12 | 3.2 | Tremolo rate |
| `WobbleDepth` | 0..1 | 0.28 | Tremolo depth |
| `BreathLevel` | 0..1 | 0.06 | Low-passed noise mixed under the voice |

A convincing "mute but still mumbling" preset is `HighCutHz` 500..650,
`DriveDb` 8..12, `WobbleDepth` 0.2..0.35 and `BreathLevel` 0.03..0.08. Lowering
`HighCutHz` further makes the speaker unintelligible; raising it makes the
effect sound like a cheap radio rather than a mumble.

### 4.3 `VoiceUnderwaterSettings`

| Field | Range | Default | Meaning |
|---|---|---|---|
| `LowCutHz` | 20..1000 | 140 | High-pass corner |
| `HighCutHz` | 100..8000 | 700 | Low-pass corner |
| `Resonance` | 0.1..8 | 1.35 | Q of the resonant peak |
| `WowHz` | 0.05..8 | 0.7 | Slow delay modulation rate |
| `WowDepth` | 0..1 | 0.35 | Delay modulation depth, scaled to 8 ms |

The effect filters and modulates the voice only. It does not synthesize bubbles,
spawn particles or decide when the player is speaking.

### 4.4 `VoiceRadioSettings`

| Field | Range | Default | Meaning |
|---|---|---|---|
| `LowCutHz` | 50..3000 | 300 | High-pass corner |
| `HighCutHz` | 500..12000 | 3200 | Low-pass corner |
| `StaticLevel` | 0..1 | 0.18 | Constant filtered noise |
| `CrackleRate` | 0..40 | 7 | Impulse crackles per second |
| `Squelch` | 0..1 | 0.12 | Probability of a dropout interval |
| `DriveDb` | 0..36 | 6 | Transmitter saturation |
| `MuteWhenSquelched` | bool | false | A dropout becomes full silence instead of attenuation |

A direct "radio mute" is a Radio slot followed by a Mute slot. A softer
interference mute is the condition path with `InterferenceHardMute`.

### 4.5 `VoicePitchSettings`

| Field | Range | Default | Meaning |
|---|---|---|---|
| `Semitones` | -24..24 | 7 | Pitch ratio, 12 is one octave |
| `WindowMs` | 8..21 | 20 | Granular window; shorter is cheaper and more artifact-prone |

The pitch shifter is time-domain. It adds up to one window of latency and does
not preserve formants by itself; pair it with a Formant slot when the result
must stay intelligible.

### 4.6 `VoiceFormantSettings`

| Field | Range | Default | Meaning |
|---|---|---|---|
| `Semitones` | -24..24 | 4 | Shift of three peaking resonators (600/1200/2400 Hz) |
| `StrengthDb` | 0..24 | 6 | Boost or cut applied by each resonator |

This is a vocal-tract colour approximation, not a spectral-envelope
extraction. It is most useful as a second slot after Pitch.

### 4.7 `VoiceDistortionSettings`

| Field | Range | Default | Meaning |
|---|---|---|---|
| `DriveDb` | 0..48 | 12 | Soft-clip drive |
| `LowCutHz` | 20..2000 | 180 | High-pass corner before the clipper |
| `HighCutHz` | 500..16000 | 5000 | Low-pass corner after the clipper |
| `BitDepth` | 2..16 | 10 | Quantizer resolution; lower is harsher |

### 4.8 `VoiceRingModulationSettings`

| Field | Range | Default | Meaning |
|---|---|---|---|
| `FrequencyHz` | 1..500 | 30 | Modulator frequency |
| `Depth` | 0..1 | 0.7 | Dry/wet amount of the multiplication |

### 4.9 `VoiceWhisperSettings`

| Field | Range | Default | Meaning |
|---|---|---|---|
| `NoiseLevel` | 0..1 | 0.35 | Noise mixed with the filtered voice |
| `LowCutHz` | 100..6000 | 900 | Removes the voiced body |
| `HighCutHz` | 1000..16000 | 6500 | Keeps the breath band |

### 4.10 Slot and chain controls

| Field | Meaning |
|---|---|
| `VoiceEffectSlot::Kind` | `None` skips the slot; otherwise one `VoiceEffectKind` |
| `VoiceEffectSlot::Mix` | 0 is fully dry, 1 is fully wet; clamped to 0..1 |
| `VoiceEffectChainSettings::Slots` | Eight fixed entries |
| `VoiceEffectChainSettings::Count` | Active entries, 0..8 |
| `Add(Slot)` | Appends until the capacity is full; returns false when full |
| `Clear()` | Resets every slot and the count |
| `Clamp()` | Clamps the count and every selected parameter group |
| `Issue()` | Returns a static message when values were clamped, otherwise null |

Chain order matters. A practical order is filter shaping, pitch, formant,
distortion or ring modulation, then mute last. A mute placed first silences the
signal before the later slots do any work.

## 5. Conditions and read-only state

### 5.1 Input state

`VoiceConditionState` is the game's sample of the world:

| Field | Meaning |
|---|---|
| `Submerged` | The source or listener is underwater |
| `Oxygen01` | Oxygen fraction, 0 empty and 1 full |
| `Interference01` | Radio interference amount, 0 clean and 1 fully jammed |

The engine does not simulate oxygen, track speaking or generate bubbles. It
reads `Submerged` to drive filtering, reads `Interference01` to drive the radio
path and passes `Oxygen01` through to `VoiceConditionOutput` for the game's HUD
and particle logic. The game owns the oxygen meter, voice activity and every
visual bubble.

### 5.2 Condition mapping

`VoiceConditionSettings` controls the two reserved slots and their smoothing.

| Field | Range | Default | Meaning |
|---|---|---|---|
| `EnableUnderwater` | bool | true | Adds or drives an underwater slot |
| `EnableInterference` | bool | true | Adds or drives a radio slot |
| `UnderwaterFadeSeconds` | 0..2 | 0.25 | Blend time when the submerged state changes |
| `UnderwaterLowCutHz` | 20..1000 | 140 | High-pass for the reserved slot |
| `UnderwaterHighCutHz` | 100..8000 | 700 | Low-pass for the reserved slot |
| `UnderwaterResonance` | 0.1..8 | 1.35 | Resonant peak Q |
| `UnderwaterWowHz` | 0.05..8 | 0.7 | Wow rate |
| `UnderwaterWowDepth` | 0..1 | 0.35 | Wow depth |
| `InterferenceFadeSeconds` | 0..2 | 0.1 | Blend time for interference |
| `InterferenceStaticLevel` | 0..1 | 0.25 | Static level at full interference |
| `InterferenceCrackleRate` | 0..60 | 10 | Crackle rate at full interference |
| `InterferenceMuteThreshold` | 0..1 | 0.9 | Threshold for the hard-mute decision |
| `InterferenceHardMute` | bool | false | Reaches zero output gain at the threshold |

If the authored chain already contains an Underwater or Radio slot, the
condition path reuses it and takes the larger of the authored and condition wet
mix. Otherwise it appends one slot, capacity permitting. The reserved slots do
not consume the authored slot count until they are appended.

### 5.3 Output state

`VoiceEffectRack::Condition()` returns:

| Field | Meaning |
|---|---|
| `Submerged` | Last input flag |
| `UnderwaterBlend` | Smoothed 0..1 wet amount |
| `Oxygen01` | Clamped oxygen fraction, passed through unchanged |
| `Interference` | Smoothed 0..1 interference |
| `OutputGain` | Condition-driven gain, 0 when hard-muted |

`VoiceSystem` exposes the same value for the local capture rack through
`LocalCondition()` and for each participant through `ParticipantCondition()`.
The game reads `Oxygen01`, its own speaking state and its own entity positions
to decide whether to spawn bubbles. The voice layer never queues bubble events,
spawns particles or awards gameplay state.

## 6. Voice positioning and the held-head case

### 6.1 Listener-side spatial settings

`VoiceSpatialSettings` is disabled by default. When enabled, every participant
with a source position gets a distance gain and a stereo pan.

| Field | Range | Default | Meaning |
|---|---|---|---|
| `Enabled` | bool | false | Enables the spatial path |
| `MinDistance` | 0.01..1000 | 1.0 | Full-volume radius |
| `MaxDistance` | `MinDistance`..10000 | 40.0 | Cutoff radius used by the mute rule |
| `Rolloff` | 0..8 | 1.0 | Inverse-distance slope outside the minimum |
| `PanWidth` | 0..1 | 1.0 | Stereo width multiplier |
| `MuteBeyondMaxDistance` | bool | false | Forces silence past the cutoff |

The gain outside the minimum is `1 / (1 + Rolloff * (Distance - MinDistance))`.
The pan is `clamp((Source.X - Listener.X) / Distance * PanWidth, -1, 1)`. The
math is also available as `EvaluateVoiceSpatial`, so a game-owned voice can use
the same placement.

### 6.2 Source position and override

```cpp
Session.SetListenerPosition(Listener);
Session.SetParticipantPosition(Player, Body);
Session.Update(DeltaSeconds);

Session.SetParticipantPositionOverride(Player, HeldHead);
Session.Update(DeltaSeconds);

Session.ClearParticipantPositionOverride(Player);
```

The override replaces the emitter used for gain and pan. The decoded stream is
not duplicated: the same voice is heard from the held head instead of the body.
For the held-head scene, this is exactly the "remove the body source and speak
from the head" routing. To silence the original body as a separate emitter, use
`SetParticipantMuted` and play the head's own line through a positioned
`DspGraph` voice.

### 6.3 Held talking head recipe

1. Replicate the held entity's world position to every client.
2. On each listening client, call `SetParticipantPositionOverride(Player,
   HeadPosition)` for the player whose head is held.
3. Apply a per-participant profile with `Chipmunk` or a custom Pitch + Formant
   chain to that same player.
4. If the head speaks its own recorded or synthesized line instead of the
   player's microphone, mute the participant and play the head line through
   `DspGraph::PlayOneShot` or `PlayStream`.
5. Position that head voice with `EvaluateVoiceSpatial` and update the voice
   with `DspGraph::SetVoiceSpatial` every frame.

The result is local to each listener: the holder can hear the squeaky head,
another player can hear the normal body voice, and a spectator can hear a
muffled version, all without changing the transmitted Opus stream.

## 7. Recipes

### 7.1 Direct mute

```cpp
Fby::VoiceEffectProfile ScopedProfile;
ScopedProfile.EnableConditions = false;
Fby::VoiceEffectSlot ScopedSlot;
ScopedSlot.Kind = Fby::VoiceEffectKind::Mute;
ScopedSlot.Mix = 1.0f;
ScopedSlot.Mute.FadeSeconds = 0.08f;
ScopedProfile.BaseChain.Add(ScopedSlot);
Voice.SetParticipantEffects(Player, ScopedProfile);
```

For an instant moderation mute, set `FadeSeconds = 0`.

### 7.2 Mumble instead of silence

```cpp
Fby::VoiceEffectProfile ScopedProfile;
ScopedProfile.EnableConditions = false;
Fby::VoiceEffectSlot ScopedSlot;
ScopedSlot.Kind = Fby::VoiceEffectKind::Muffle;
ScopedSlot.Mix = 1.0f;
ScopedSlot.Muffle.HighCutHz = 560.0f;
ScopedSlot.Muffle.Resonance = 1.2f;
ScopedSlot.Muffle.DriveDb = 11.0f;
ScopedSlot.Muffle.WobbleHz = 3.4f;
ScopedSlot.Muffle.WobbleDepth = 0.32f;
ScopedSlot.Muffle.BreathLevel = 0.05f;
ScopedProfile.BaseChain.Add(ScopedSlot);
Voice.SetParticipantEffects(Player, ScopedProfile);
```

This keeps the speaker's rhythm, so the player knows someone is talking, but
removes most intelligibility. Lower `HighCutHz` to 450 for a stronger effect.

### 7.3 Underwater listener

```cpp
Fby::VoiceEffectProfile ScopedProfile;
ScopedProfile.EnableConditions = true;
ScopedProfile.Conditions.UnderwaterFadeSeconds = 0.25f;
ScopedProfile.Conditions.UnderwaterHighCutHz = 620.0f;

// Configure once, when the listener enters or leaves the underwater profile.
for (std::uint8_t Player = 0; Player < 8; ++Player)
{
    if (Session.Participant(Player) != nullptr)
    {
        Voice.SetParticipantEffects(Player, ScopedProfile);
    }
}

// Per frame: only the condition changes.
for (std::uint8_t Player = 0; Player < 8; ++Player)
{
    if (Session.Participant(Player) != nullptr)
    {
        Fby::VoiceConditionState ScopedState;
        ScopedState.Submerged = ListenerUnderwater;
        ScopedState.Oxygen01 = LocalOxygen;
        Voice.SetParticipantCondition(Player, ScopedState);
    }
}
```

If the listener is underwater, every remote voice should get the same condition.
If the speaker is underwater, set `Submerged` only on that speaker's condition.
The profile setter is not a per-frame call; it resets the chain history.

### 7.4 Oxygen condition without engine-owned bubbles

The engine does not generate bubbles. It provides the muffled voice and the
read-only condition snapshot; the game decides when a bubble particle is born.

```cpp
Fby::VoiceConditionState ScopedState;
ScopedState.Submerged = true;
ScopedState.Oxygen01 = 0.18f;
Voice.SetParticipantCondition(Player, ScopedState);

Voice.Tick(DeltaSeconds, Session);

const Fby::VoiceConditionOutput* ScopedOutput = Voice.ParticipantCondition(Player);
if (ScopedOutput != nullptr && ScopedOutput->Submerged && ScopedOutput->Oxygen01 < 0.35f)
{
    const Fby::VoiceParticipant* ScopedSpeaker = Session.Participant(Player);
    if (ScopedSpeaker != nullptr && ScopedSpeaker->Talking)
    {
        SpawnBubbles(PlayerPosition, GameOwnedBubbleCount, GameOwnedBubbleStrength);
    }
}
```

`Oxygen01` is a pass-through value. The game owns the oxygen meter, the
speaking test and the bubble visuals; the voice layer only applies the
underwater muffling and exposes `UnderwaterBlend`, `Oxygen01` and `OutputGain`.
Do not expect `VoiceSystem` to queue particle events.

### 7.5 Pitch, formant and robot voices

```cpp
Fby::VoiceEffectChainSettings ScopedChain =
    Fby::VoiceEffectPresetChain(Fby::VoiceEffectPresetKind::Chipmunk);
ScopedChain.Slots[0].Pitch.Semitones = 9.0f;
ScopedChain.Slots[1].Formant.StrengthDb = 4.0f;

Fby::VoiceEffectProfile ScopedProfile;
ScopedProfile.EnableConditions = false;
ScopedProfile.BaseChain = ScopedChain;
Voice.SetParticipantEffects(Player, ScopedProfile);
```

For a robot, use `RingModulation` at 20..40 Hz with `Depth` 0.8..1.0, followed
by a small amount of Distortion. For a whisper, use `Whisper` with
`NoiseLevel` 0.25..0.45.

### 7.6 Radio interference and radio mute

```cpp
Fby::VoiceEffectProfile ScopedProfile;
ScopedProfile.Conditions.EnableInterference = true;
ScopedProfile.Conditions.InterferenceStaticLevel = 0.3f;
ScopedProfile.Conditions.InterferenceCrackleRate = 12.0f;
ScopedProfile.Conditions.InterferenceHardMute = false;
Voice.SetParticipantEffects(Player, ScopedProfile);

Fby::VoiceConditionState ScopedState;
ScopedState.Interference01 = 0.65f;
Voice.SetParticipantCondition(Player, ScopedState);
```

For a radio with a hard cutoff, set `InterferenceHardMute = true` and
`InterferenceMuteThreshold = 0.85`. For a direct mute that is not tied to
interference, use the `Muted` preset or a Mute slot.

### 7.7 Radio on the uplink

```cpp
Fby::VoiceEffectProfile ScopedProfile;
ScopedProfile.EnableConditions = false;
Fby::VoiceEffectSlot ScopedSlot;
ScopedSlot.Kind = Fby::VoiceEffectKind::Radio;
ScopedSlot.Mix = 1.0f;
ScopedSlot.Radio.LowCutHz = 350.0f;
ScopedSlot.Radio.HighCutHz = 2800.0f;
ScopedProfile.BaseChain.Add(ScopedSlot);
Voice.SetUplinkEffects(ScopedProfile);
```

This is the correct choice when every listener must hear the same radio voice.
If only one listener should hear it, use the downlink path instead.

### 7.8 Fully custom chain

```cpp
Fby::VoiceEffectProfile ScopedProfile;
ScopedProfile.EnableConditions = false;

Fby::VoiceEffectSlot ScopedMuffle;
ScopedMuffle.Kind = Fby::VoiceEffectKind::Muffle;
ScopedMuffle.Mix = 0.55f;
ScopedMuffle.Muffle.HighCutHz = 700.0f;

Fby::VoiceEffectSlot ScopedPitch;
ScopedPitch.Kind = Fby::VoiceEffectKind::Pitch;
ScopedPitch.Mix = 1.0f;
ScopedPitch.Pitch.Semitones = 4.0f;
ScopedPitch.Pitch.WindowMs = 26.0f;

ScopedProfile.BaseChain.Add(ScopedMuffle);
ScopedProfile.BaseChain.Add(ScopedPitch);
Voice.SetParticipantEffects(Player, ScopedProfile);
```

Keep at most one pitch-style slot per chain. Each slot owns a delay line, but
stacking two pitch shifters is rarely useful and adds latency.

### 7.9 Reading state without changing audio

```cpp
const Fby::VoiceConditionOutput& ScopedLocal = Voice.LocalCondition();
const Fby::VoiceConditionOutput* ScopedRemote = Voice.ParticipantCondition(Player);
if (ScopedRemote != nullptr)
{
    Hud.ShowVoiceGain(ScopedRemote->OutputGain);
    Hud.ShowInterference(ScopedRemote->Interference);
}
```

Condition outputs are read-only snapshots. Changing them does not change the
DSP; change the profile or the condition state instead.

## 8. Testing and budgets

The voice effect test covers:

| Test | What it proves |
|---|---|
| `voice_effects` | Presets and clamping, direct mute, muffle frequency response, pitch up/down, underwater condition readout, radio hard mute, spatial gain/pan and position override, a custom chain, the decode-sink insertion point |

Existing voice tests remain the regression gate:

| Test | Scope |
|---|---|
| `voice_dsp` | Microphone chain, gate, AGC and limiter |
| `voice_aec` | Echo cancellation and drift |
| `voice_network` | Opus, jitter, relay/mesh and ducking |
| `voice_system` | Capture to mixer with the new effect rack |
| `voice_bridge` | Encrypted relay path |
| `voice_call` | Four-player call |
| `voice_pipeline` | Ring math, stream voices and session policy |

Cost expectations at 48 kHz:

- an inactive rack costs one branch per block;
- an active slot costs one sample loop, a few biquads and at most one delay
  read;
- a pitch slot adds up to one window of algorithmic latency (8..21 ms);
- a rack owns about 70 KiB of fixed state, so eight participants plus the local
  capture path remain under 1 MiB of effect memory;
- no effect path allocates, locks or calls into the audio callback.

## 9. Integration checklist

- The game owns oxygen, submerged, interference, speaking and bubbles.
- Text and voice use the same player ids and the same local mute list.
- All remote text is sanitized after authentication.
- All voice effects are configured before the participant is bound, or updated
  through the per-player setters.
- `VoiceSystem::Tick` runs every frame that should advance condition smoothing
  and the effect rack.
- `VoiceSession::Update` runs every frame so pan and gain reach the mixer.
- Captions are fed from the same sanitized text and the same voice activity
  state.
- A held head has a replicated position, a per-listener position override and
  a pitch/formant profile.
- A radio mute is a deliberate chain decision: Radio + Mute for silence, or the
  condition hard-mute for interference-driven silence.
- The effect profile is capped at eight slots and validated with `Issue()`.
